Stop Spoonfeeding the Model

The fastest way to make an agent worse is to explain too much. We mistake control for rigor — and the prompt rots exactly like bad code.

By Panshul Jindal · 28 August 2026 · 8 min read

The tell

It works. That's the problem.

An over-instructed agent takes about ten seconds to spot. The system prompt reads like defensive code I'd have written on a day I didn't trust the runtime — every branch spelled out, every edge case pinned down in prose, nine numbered steps for something the model would have nailed in one. And here's what keeps the pattern alive: it works. The demo passes. The feature ships. Nobody looks again.

That "it works" is where the rot hides. Bad code works too. I can solve almost any problem with enough nested conditionals and copy-paste — the program runs, the tests go green, and I've quietly signed up for the next six months of maintenance. An over-stuffed prompt is that exact move in a different file. It passes today and breaks on the next model version, because I hardcoded behavior the model was about to handle on its own.

So I've started treating prompts the way I treat code I'll have to maintain, because that's what they are. A prompt is not an asset you pile up. It's a liability you carry.

Why we do it

Control feels like diligence.

Nobody over-instructs on purpose. It's a good instinct wearing the wrong outfit. You want the thing to behave in front of real users, so you reach for what makes code behave: nail down everything, leave nothing to chance. But an agent isn't a function I'm implementing. It's a capable teammate I'm briefing — and every step I narrate for it is a step I've taken away from it. The more I script, the worse it does the moment reality stops matching my script. In production, reality never matches the script.

There's a second reason, and it's the uncomfortable one: we get attached to our prompts the way we get attached to our PRs. That instruction block is something I wrote, defended in review, and now own — so it only grows. Every incident bolts on another line (never do X again). Every review adds a clause. Nobody ever deletes anything, because deleting feels like admitting the line was never load-bearing. That's not engineering. That's ego with a commit message.

Stop instructing the model. Hand it the suggestions and the gotchas, then be patient with the context. You're not writing a hack — you're writing a briefing.

A way to picture it

The brain doesn't move the fingers.

Picture yourself picking up a coffee cup. Your brain doesn't send a numbered list to each finger — flex this knuckle thirty degrees, two newtons of grip, rotate the wrist. It sets an intent ("grab the cup"), maybe one caution ("the handle's hot"), and trusts the hand to do the rest. Try to consciously drive every tendon and you'll be slower, clumsier, and you'll drop it.

That's an agent. The LLM is the brain — it thinks, it orchestrates, it decides what to do next. The tools are the hands — they're what actually reach out and act. When I over-instruct, I'm consciously controlling each finger: scripting the exact tool calls, in order, for a body that already knows how to move. It works in the demo the same way you can pick up a cup slowly while staring at your hand. It falls apart the second the cup is somewhere you didn't expect.

So I brief the brain and hand it good tools — then I let it reach.

refund-agent  —  scripting the hands vs. briefing the brain
−lookup_order(id) → read status → if "settled",
−check_refund_policy() → if eligible, issue_refund(),
−then send_email("refund_confirmed"), then log().
+Tools: lookup_order, issue_refund, send_email.
+Resolve the refund if it's under $50 and the charge has settled.
+Gotcha: issue_refund isn't idempotent — never call it twice.

Same hands. The second version lets the brain decide which one to use, and when.

How I build now

Five rules I actually follow.

None of this is about writing less to look clever. It's about spending my words where they compound instead of where they decay.

01

Suggest, don't dictate.

I give the model a rule of thumb, not a screenplay. "When something can't be undone, confirm before you do it" holds across a thousand situations I'll never enumerate. "If the message says cancel, open screen three" holds in exactly one. I write the heuristic and let the model apply judgment — because judgment is the whole reason I reached for a model instead of an if-statement.

02

Ship the gotchas, not the checklist.

The model finds the happy path without me. What it can't know is the landmine I stepped on last week — so that's what I write down: the payments API that says paid before the charge settles, the search index that lags writes by a couple of seconds, the "user" that's null for accounts created before 2021, the webhook that fires twice on retry. Everything else, I let it work out. A good prompt reads less like a manual and more like me leaning over to say — before you start, watch out for this.

03

Patience is the technique.

The lazy move is to keep tuning the sentence. The move that works is slower: give the model what it's actually missing. The domain rules. The real constraints. What "done" means here, specifically. The two things that always trip people up in this system. That's not a prompt trick — it's just doing the homework. And it's the part everyone skips, because homework doesn't feel clever.

04

Aim for the right altitude.

There's a height I'm aiming for. Too low — if-this-then-that, hardcoded — and it shatters on the first real user I didn't imagine. Too high — "be helpful, use good judgment" — and it just guesses. I aim for the altitude a sharp teammate would want on day one: the goal, the boundaries, the traps, and room to think. Nothing I'd have to rewrite the day the model gets better.

05

Treat the prompt like code you'll delete.

Every line I add is a line someone maintains, audits, and second-guesses the day the model shifts underneath it. So I hold each one to that bar: if a line only restates what the model already does well, it isn't a guardrail — it's debt. Most of my best prompt edits have been deletions.

In practice

The same move, three more times.

Different agents, same discipline: cut the steps the model can infer, keep the one fact it can't. Every one of these got better after the diet.

notification-agent  —  before / after
−Write push copy. Max 40 chars. Start with an emoji.
−Use urgency. Mention the % off. Give me two A/B variants.
−Tone: friendly, not pushy. Never ALL CAPS. Never…
+Draft two push variants for this promo.
+Gotcha: the preview truncates near 40 chars on Android — lead with the value, not the emoji.

It already knows what good push copy looks like. It doesn't know your truncation limit.

ingest-agent  —  before / after
−Step 1: read the file. Step 2: check each column exists.
−Step 3: parse the dates. Step 4: on a bad row, log and skip.
−Step 5: dedupe. Step 6: insert. Step 7: …
+Load this vendor CSV into the orders table; skip and report bad rows.
+Gotcha: this vendor sends dates as MM/DD/YYYY. Everyone else sends ISO.

Seven steps it can infer. One quirk it can't.

scheduling-agent  —  before / after
−Check the calendar. Convert time zones. Add a 15-min buffer.
−Prefer mornings. Avoid Fridays. Confirm before booking. Then…
+Book a 30-min intro with the client this week.
+Gotcha: their calendar is IST; ours renders UTC — double-check the offset.

When to meet is a judgment call. The timezone trap is yours to flag.

The point

Brief it. Then trust it.

Next time you're about to add the tenth instruction, delete the first nine and watch what breaks. In my experience, less than you feared. Give the model the map and the landmines, then get out of its way. That's not laziness — it's the same taste that separates software I'm proud of from software that merely runs.
